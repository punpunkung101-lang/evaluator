# Project Brief: แพลตฟอร์มประเมินประสิทธิภาพและประสิทธิผลระบบสารสนเทศ

> เอกสารส่งมอบแนวคิดและข้อกำหนดเบื้องต้นให้ AI Agent / Development Agent
> ใช้ต่อยอดออกแบบและพัฒนาเว็บไซต์\
> ชื่อโครงการชั่วคราว: **ระบบประเมินคุณภาพระบบสารสนเทศ (Information System
> Evaluation Platform)**

------------------------------------------------------------------------

## 1. ภาพรวมโครงการ (Project Overview)

พัฒนาเว็บไซต์กลางสำหรับสร้างแบบประเมินและประเมินประสิทธิภาพ ประสิทธิผล
และคุณภาพของระบบสารสนเทศภายในหน่วยงาน
โดยเว็บไซต์นี้ต้องสามารถนำกลับไปใช้ประเมินระบบออนไลน์ได้หลายประเภท
ไม่จำกัดเฉพาะระบบแจ้งซ่อมและบำรุงรักษา

ตัวอย่างระบบที่นำมาประเมิน: - ระบบแจ้งซ่อมและบำรุงรักษา - ระบบจองห้องหรือทรัพยากร -
ระบบจัดการเอกสาร - ระบบบริการบุคลากร - ระบบสารสนเทศอื่น ๆ ของหน่วยงาน

**แนวคิดหลัก:** สร้างแพลตฟอร์มประเมินผลแบบ Dynamic / Configurable
ไม่ใช่แบบสอบถามที่เขียนตายตัวสำหรับระบบใดระบบหนึ่ง ผู้ดูแลต้องสามารถสร้างชุดประเมิน
เพิ่ม/แก้ไข/ปิดคำถาม กำหนดหมวดตัวชี้วัด ประเภทคำตอบ และเงื่อนไขการแสดงคำถามได้เอง

ผลลัพธ์ต้องช่วยตอบคำถามผู้บริหารได้ว่า: 1. ระบบใช้งานได้ดีเพียงใดในมุมมองผู้ใช้ 2.
ระบบช่วยให้การทำงานมีประสิทธิภาพและเกิดผลสำเร็จหรือไม่ 3.
ผู้ใช้พบปัญหาหรืออุปสรรคตรงไหน 4. จุดใดควรได้รับการปรับปรุงก่อน 5.
มีข้อมูลเพียงพอหรือไม่ในการตัดสินใจพัฒนาระบบต่อ

## 2. หลักการออกแบบ (Core Concept)

### 2.1 ใช้โครงสร้างประเมิน 2 ระดับ

**A. Core Indicators --- ตัวชี้วัดกลาง**

เป็นตัวชี้วัดมาตรฐานที่ใช้ร่วมกันได้กับระบบสารสนเทศหลายประเภท เช่น: -
ความง่ายและความสะดวกในการใช้งาน (Usability) - ประสิทธิภาพด้านเวลาและขั้นตอน
(Efficiency) - ประสิทธิผลในการดำเนินงาน (Effectiveness) -
ความถูกต้องและครบถ้วนของข้อมูล (Data Quality) - การติดตามและความโปร่งใส
(Tracking & Transparency) --- แสดงเมื่อเกี่ยวข้อง - ความเสถียรและความน่าเชื่อถือ
(Reliability) - ความพึงพอใจและความต้องการใช้งานต่อ (User Satisfaction)

**B. Specific Indicators --- ตัวชี้วัดเฉพาะระบบ**

เป็นตัวชี้วัดที่ออกแบบตามหน้าที่และ Workflow ของระบบนั้น ๆ เช่น
ระบบแจ้งซ่อมมีเรื่องการรับแจ้ง มอบหมายงาน จัดซื้อวัสดุ ประสานบริษัท และปิดงาน

ห้ามบังคับให้ทุกระบบต้องใช้ตัวชี้วัดเฉพาะชุดเดียวกัน
ผู้ดูแลต้องเลือกเปิด/ปิดและเพิ่มหมวดเฉพาะได้

### 2.2 อย่าใช้คะแนน 1--5 กับทุกคำถาม

แบบประเมินต้องผสมคำถามหลายประเภท: - Rating 1--5 สำหรับการรับรู้หรือความคิดเห็น -
ข้อเท็จจริงแบบตัวเลือก เช่น เคยใช้ระบบเดิมหรือไม่ - ความถี่ เช่น พบปัญหาบ่อยเพียงใด -
จำนวนหรือช่วงเวลา เช่น ใช้เวลาดำเนินการเท่าใด - Checkbox สำหรับเลือกปัญหาหลายข้อ -
Ranking สำหรับจัดลำดับความสำคัญ - คำถามปลายเปิดสำหรับข้อเสนอแนะ

**ข้อควรระวัง:** ความพึงพอใจไม่ใช่หลักฐานประสิทธิภาพโดยตรง ต้องแยกผลการรับรู้ของผู้ใช้
ออกจากข้อมูลสถิติการทำงานจริงของระบบ

### 2.3 ออกแบบตามบทบาท (Role-based)

ผู้ตอบแต่ละคนควรเห็นคำถามที่เกี่ยวข้องกับบทบาทของตนเท่านั้น เช่น
ผู้แจ้งซ่อมไม่จำเป็นต้องตอบคำถามเกี่ยวกับการจัดซื้อพัสดุ

### 2.4 รองรับคำถามแบบมีเงื่อนไข (Conditional Questions)

ตัวอย่าง: - หากเคยใช้ระบบเดิม ให้แสดงคำถามเปรียบเทียบก่อนและหลัง -
หากไม่เคยใช้ระบบเดิม ให้ข้ามคำถามเปรียบเทียบ - หากเลือกบทบาทเจ้าหน้าที่พัสดุ
ให้แสดงคำถามเฉพาะพัสดุ - หากตอบว่าเคยพบปัญหา ให้แสดงคำถามรายละเอียดปัญหา -
หากตอบว่าไม่พบปัญหา ให้ข้ามรายละเอียดปัญหา

## 3. User Journey / โครงสร้างแบบประเมิน

แบบประเมินฝั่งผู้ใช้งานควรแบ่งเป็น 4 ขั้นตอนหลัก และมีหน้าสรุปก่อนส่งคำตอบ

### ขั้นที่ 1: ประสบการณ์การใช้ระบบเดิม

**คำถามหลัก:** ท่านเคยใช้งานระบบก่อนที่จะพัฒนาเป็นระบบออนไลน์หรือไม่?

ประเภท: Radio (เลือกได้หนึ่งข้อ) - เคยใช้งานระบบเดิม - ไม่เคยใช้งานระบบเดิม -
เคยใช้วิธีแจ้ง/ดำเนินงานผ่านเอกสาร โทรศัพท์ หรือช่องทางอื่น แต่ไม่เคยใช้ระบบเดิม

หากตอบว่าเคย ให้แสดงคำถามเพิ่มเติม: 1. ก่อนมีระบบออนไลน์ ท่านใช้ช่องทางใด? -
เอกสาร/แบบฟอร์มกระดาษ - โทรศัพท์ - แจ้งด้วยวาจา - LINE หรือแอปสนทนา - อีเมล -
ระบบสารสนเทศเดิม - อื่น ๆ 2. ระบบเดิมมีข้อจำกัดหรือปัญหาอะไรบ้าง? (Checkbox) 3.
เมื่อเทียบกับระบบเดิม ระบบออนไลน์ช่วยให้ใช้งานสะดวกขึ้นเพียงใด? (Rating 1--5) 4.
ระบบออนไลน์ช่วยลดขั้นตอนการทำงานจากเดิมเพียงใด? (Rating 1--5) 5.
ระบบออนไลน์ช่วยให้ติดตามความคืบหน้าได้ดีขึ้นเพียงใด? (Rating 1--5)

### ขั้นที่ 2: ข้อมูลทั่วไปและลักษณะการใช้งาน

ใช้ Dropdown / Radio / Checkbox ตามความเหมาะสม
และต้องให้ผู้ดูแลแก้ไขรายการตัวเลือกได้

ข้อมูลที่ควรเก็บ: 1. บทบาทของผู้ตอบ 2. หน่วยงาน/สังกัด 3. ลักษณะการใช้งานระบบ 4.
ความถี่ในการใช้งาน 5. ระยะเวลาที่ใช้งานระบบ 6. อุปกรณ์ที่ใช้เข้าใช้งาน 7.
ประเภทงานหรือกระบวนการที่เกี่ยวข้อง (ถ้ามี)

ตัวอย่างตัวเลือกบทบาทจากระบบแจ้งซ่อม: - ผู้แจ้งซ่อม (บุคลากรทั่วไป) -
หัวหน้าสำนักงานเลขานุการ / ผู้รับเรื่องและมอบหมายงาน - เจ้าหน้าที่ซ่อม - เจ้าหน้าที่พัสดุ -
ผู้บริหาร - อื่น ๆ

ตัวอย่างความถี่: - ทุกวัน - 3--5 วันต่อสัปดาห์ - 1--2 วันต่อสัปดาห์ - 1--3 ครั้งต่อเดือน -
น้อยกว่า 1 ครั้งต่อเดือน

ตัวอย่างระยะเวลาการใช้งาน: - น้อยกว่า 1 เดือน - 1--3 เดือน - 4--6 เดือน - 7--12
เดือน - มากกว่า 1 ปี

ตัวอย่างอุปกรณ์: - คอมพิวเตอร์ - โน้ตบุ๊ก - โทรศัพท์มือถือ - แท็บเล็ต

สำหรับระบบแจ้งซ่อมโดยเฉพาะ: - ประเภทงาน: อาคาร/สถานที่, ครุภัณฑ์, อุปกรณ์ IT,
ไฟฟ้า, ประปา, อื่น ๆ - เส้นทางงาน: Path A ซ่อมเอง, Path B จัดซื้อวัสดุ/อะไหล่, Path
C ประสานบริษัทภายนอก - สถานะงาน: แจ้งซ่อม, มอบหมายงาน, อยู่ระหว่างดำเนินการ,
จัดซื้อวัสดุ, ประสานบริษัท, อนุมัติ/รอซ่อม, เสร็จสิ้น, ยกเลิก

ข้อกำหนด: - บทบาทและหน่วยงานควรเป็นข้อมูลที่ผู้ดูแลกำหนดได้ -
บางคำถามเลือกได้หลายข้อ - มีตัวเลือก "อื่น ๆ" และ "ไม่เกี่ยวข้อง" เมื่อเหมาะสม -
ไม่ควรบังคับให้ผู้ตอบระบุข้อมูลส่วนบุคคลที่ไม่จำเป็นต่อการวิเคราะห์

### ขั้นที่ 3: ตัวชี้วัดประเมินระบบ

ใช้ Core Indicators เป็นแกนกลาง และแสดง Specific Indicators
ตามระบบ/บทบาทที่เกี่ยวข้อง

#### 3.1 Usability --- ความง่ายและความสะดวกในการใช้งาน

-   U1 ระบบมีรูปแบบการใช้งานที่เข้าใจง่าย
-   U2 เมนูและฟังก์ชันจัดวางเหมาะสมและค้นหาได้ง่าย
-   U3 ขั้นตอนการใช้งานไม่ซับซ้อน
-   U4 สามารถดำเนินการในส่วนที่รับผิดชอบได้ด้วยตนเอง
-   U5 ระบบรองรับอุปกรณ์ที่ใช้งานได้อย่างเหมาะสม

#### 3.2 Efficiency --- ประสิทธิภาพด้านเวลาและขั้นตอน

-   E1 ระบบช่วยลดระยะเวลาในการดำเนินงาน
-   E2 ระบบช่วยลดขั้นตอนการประสานงานระหว่างผู้เกี่ยวข้อง
-   E3 ระบบช่วยลดการใช้เอกสารหรือการบันทึกข้อมูลซ้ำซ้อน
-   E4 ระบบช่วยลดภาระงานในการปฏิบัติงาน
-   E5 ระบบช่วยให้การดำเนินงานในแต่ละขั้นตอนรวดเร็วขึ้น

คำถามเชิงข้อเท็จจริงเพิ่มเติม: - โดยปกติใช้เวลาดำเนินการผ่านระบบประมาณเท่าใด? -
เคยต้องติดต่อสอบถามความคืบหน้านอกระบบหรือไม่? - ต้องกรอกข้อมูลซ้ำหรือแก้ไขข้อมูลกี่ครั้ง?

#### 3.3 Effectiveness --- ประสิทธิผลในการดำเนินงาน

-   EF1 ระบบช่วยส่งต่อรายการไปยังผู้รับผิดชอบได้ถูกต้อง
-   EF2 ระบบช่วยให้การมอบหมายงานมีความชัดเจน
-   EF3 ระบบสนับสนุนให้ดำเนินงานตามขั้นตอนที่กำหนด
-   EF4 ระบบช่วยให้ดำเนินงานจนบรรลุผลสำเร็จ
-   EF5 ผลลัพธ์จากการดำเนินงานตรงตามความต้องการของผู้ใช้

คำถามเชิงข้อเท็จจริง: - งาน/คำขอของท่านอยู่ในสถานะใด: เสร็จสิ้น / อยู่ระหว่างดำเนินการ
/ ยกเลิก / ยังไม่ได้รับการดำเนินการ - ผลการดำเนินงานตรงตามความต้องการหรือไม่:
ครบถ้วน / บางส่วน / ไม่สำเร็จ / ยังประเมินไม่ได้

#### 3.4 Data Quality --- ความถูกต้องและครบถ้วนของข้อมูล

-   D1 ข้อมูลที่ระบบบันทึกมีความถูกต้อง
-   D2 ช่องข้อมูลครอบคลุมรายละเอียดที่จำเป็น
-   D3 ระบบรองรับการแนบเอกสารหรือภาพประกอบได้เหมาะสม
-   D4 ข้อมูลการดำเนินงานมีความครบถ้วน
-   D5 ระบบช่วยลดความผิดพลาดจากการบันทึกหรือส่งต่อข้อมูล

#### 3.5 Tracking & Transparency --- การติดตามและความโปร่งใส

แสดงเมื่อระบบมี Workflow หรือการติดตามสถานะ - T1 สามารถตรวจสอบสถานะได้สะดวก -
T2 สถานะมีความชัดเจนและเข้าใจง่าย - T3
สามารถตรวจสอบผู้รับผิดชอบในแต่ละขั้นตอนได้เหมาะสม - T4
สามารถติดตามความคืบหน้าโดยไม่ต้องสอบถามนอกระบบ - T5
ระบบแจ้งเตือนเมื่อมีการเปลี่ยนแปลงสถานะได้เหมาะสม

#### 3.6 Reliability --- ความเสถียรและความน่าเชื่อถือ

-   R1 ระบบสามารถเข้าใช้งานได้อย่างต่อเนื่อง
-   R2 ระบบตอบสนองได้รวดเร็ว
-   R3 ระบบไม่เกิดข้อผิดพลาดระหว่างใช้งานบ่อยครั้ง
-   R4 ระบบบันทึกข้อมูลได้ถูกต้องและไม่สูญหาย
-   R5 ระบบมีความปลอดภัยเหมาะสมกับการใช้งานของหน่วยงาน

#### 3.7 User Satisfaction --- ความพึงพอใจและความต้องการใช้งานต่อ

-   S1 โดยภาพรวมพึงพอใจต่อระบบ
-   S2 ระบบตอบสนองต่อความต้องการในการปฏิบัติงาน
-   S3 มีความต้องการใช้งานระบบต่อไป
-   S4 เห็นว่าระบบมีประโยชน์ต่อหน่วยงาน

**มาตราส่วน Rating 1--5** - 5 = มากที่สุด - 4 = มาก - 3 = ปานกลาง - 2 =
น้อย - 1 = น้อยที่สุด - N/A = ไม่สามารถประเมินได้ / ไม่เกี่ยวข้อง (ไม่นำมาคำนวณ)

### ขั้นที่ 4: ปัญหา ความต้องการ และข้อเสนอแนะ

## 4. คำถามเฉพาะตามบทบาท (Role-based Questions)

ระบบต้องเลือกแสดงคำถามตามบทบาทที่ผู้ตอบเลือกในขั้นที่ 2

### 4.1 ผู้แจ้งซ่อม / ผู้ใช้บริการ

-   การกรอกข้อมูลแจ้งซ่อมสะดวกหรือไม่
-   สามารถแนบรูปภาพประกอบได้สะดวกหรือไม่
-   ได้รับการแจ้งเตือนเมื่อสถานะเปลี่ยนหรือไม่
-   สามารถติดตามผลการดำเนินงานได้ด้วยตนเองหรือไม่
-   สามารถตรวจสอบผลหลังดำเนินงานได้หรือไม่

### 4.2 ผู้รับเรื่อง / ผู้มอบหมายงาน

-   ตรวจสอบคำขอได้สะดวกหรือไม่
-   กำหนดระดับความเร่งด่วนได้เหมาะสมหรือไม่
-   มอบหมายงานไปยังผู้รับผิดชอบได้ถูกต้องหรือไม่
-   ตรวจสอบงานค้างได้สะดวกหรือไม่
-   ระบบช่วยลดภาระการติดตามงานหรือไม่

### 4.3 เจ้าหน้าที่ปฏิบัติงาน / เจ้าหน้าที่ซ่อม

-   เข้าถึงรายละเอียดคำขอได้ครบถ้วนหรือไม่
-   ตรวจสอบประวัติและไฟล์แนบได้หรือไม่
-   จัดลำดับความสำคัญของงานได้หรือไม่
-   อัปเดตสถานะได้สะดวกหรือไม่
-   บันทึกผลและแนบภาพหลังดำเนินงานได้หรือไม่

### 4.4 เจ้าหน้าที่พัสดุ

-   รายละเอียดวัสดุ/อะไหล่ที่ต้องจัดซื้อครบถ้วนหรือไม่
-   บันทึกข้อมูลการจัดซื้อและค่าใช้จ่ายได้สะดวกหรือไม่
-   ติดตามสถานะการจัดซื้อได้หรือไม่
-   บันทึกการรับวัสดุและส่งต่อให้ผู้ปฏิบัติงานได้หรือไม่

### 4.5 ผู้บริหาร

-   ตรวจสอบภาพรวมจำนวนรายการได้สะดวกหรือไม่
-   รายงานมีข้อมูลเพียงพอต่อการตัดสินใจหรือไม่
-   ตรวจสอบรายการค้างดำเนินการได้หรือไม่
-   ตรวจสอบค่าใช้จ่ายได้ชัดเจนหรือไม่
-   ระบบช่วยติดตามประสิทธิภาพการดำเนินงานได้หรือไม่

หมายเหตุ: คำถามเหล่านี้เป็นตัวอย่างสำหรับระบบแจ้งซ่อม ต้องเปิดให้ผู้ดูแลแก้ไข เพิ่ม หรือลบได้
ไม่ควร hard-code ลงในระบบ

## 5. รูปแบบคำถามที่ระบบต้องรองรับ

ระบบจัดการแบบประเมินควรรองรับ Question Types อย่างน้อยดังนี้:

  Type           การใช้งาน
  -------------- ----------------------------
  Rating 1--5    ประเมินระดับความคิดเห็น/การรับรู้
  Dropdown       เลือกหนึ่งรายการจากรายการ
  Radio          เลือกหนึ่งคำตอบ
  Checkbox       เลือกได้หลายคำตอบ
  Short Answer   คำตอบข้อความสั้น
  Long Answer    คำตอบข้อความยาว
  Number         จำนวนหรือตัวเลข
  Date           วันที่
  Yes/No         ใช่/ไม่ใช่
  Ranking        จัดลำดับความสำคัญ

ความสามารถเพิ่มเติม: - ตั้งค่าคำถามบังคับตอบหรือไม่บังคับตอบ -
กำหนดคำอธิบายประกอบคำถาม - กำหนดตัวเลือกและตัวเลือก "อื่น ๆ" -
กำหนดจำนวนตัวเลือกสูงสุดที่เลือกได้ - กำหนดเงื่อนไขแสดง/ซ่อนคำถาม -
จัดลำดับคำถามและหมวดหมู่ได้ - เปิด/ปิดคำถามโดยไม่ลบข้อมูลเดิม -
กำหนดว่าคำถามใช้คำนวณคะแนนหรือเป็นข้อมูลประกอบเท่านั้น

## 6. ความสามารถฝั่งผู้ดูแลระบบ (Admin / Form Builder)

### 6.1 จัดการแบบประเมิน

-   สร้างแบบประเมินหลายชุด แยกตามระบบสารสนเทศ
-   กำหนดชื่อ คำอธิบาย วัตถุประสงค์ และช่วงเวลาเปิดรับคำตอบ
-   เปิด/ปิดแบบประเมิน
-   ทำสำเนาแบบประเมินเดิมเพื่อนำไปใช้กับระบบอื่น
-   เก็บเวอร์ชันของแบบประเมิน เพื่อให้ตรวจสอบได้ว่าคำตอบชุดหนึ่งตอบแบบประเมินเวอร์ชันใด

### 6.2 จัดการหมวดและตัวชี้วัด

-   เพิ่ม/แก้ไข/ลบ/ปิดหมวดตัวชี้วัด
-   แยก Core Indicators และ Specific Indicators
-   กำหนดลำดับหมวด
-   กำหนดว่าหมวดใดแสดงกับบทบาทใด
-   กำหนดว่าหมวดใดเกี่ยวข้องกับระบบใด

### 6.3 จัดการคำถาม

-   เพิ่ม/แก้ไข/ลบ/ปิดคำถาม
-   เลือกประเภทคำตอบ
-   กำหนดตัวเลือกคำตอบ
-   กำหนด required / optional
-   กำหนดเงื่อนไขแสดงคำถาม
-   กำหนดการคำนวณคะแนน
-   Preview แบบประเมินก่อนเผยแพร่

### 6.4 จัดการผลประเมิน

-   ดูจำนวนผู้ตอบและอัตราการตอบ
-   ดูผลรวมและผลแยกตามหมวด
-   เปรียบเทียบผลตามบทบาท หน่วยงาน และช่วงเวลา
-   ดูคำตอบปลายเปิดและปัญหาที่ถูกรายงาน
-   ส่งออก Excel / PDF
-   กรองข้อมูลตามระบบ แบบประเมิน บทบาท หน่วยงาน และช่วงเวลา

## 7. Dashboard สำหรับผู้บริหาร

Dashboard ต้องแสดงข้อมูลที่ช่วยตัดสินใจ ไม่ใช่เพียงแสดงกราฟตกแต่ง

### 7.1 ภาพรวม

-   จำนวนผู้ตอบแบบประเมิน
-   จำนวนผู้ใช้งานที่ได้รับเชิญ (ถ้ามีข้อมูล)
-   อัตราการตอบแบบประเมิน
-   คะแนนเฉลี่ยภาพรวม
-   คะแนนเฉลี่ยแยกตามหมวดตัวชี้วัด

### 7.2 วิเคราะห์จุดแข็งและจุดที่ควรปรับปรุง

-   หมวดที่ได้คะแนนสูงสุด
-   หมวดที่ได้คะแนนต่ำสุด
-   คำถามที่ได้คะแนนต่ำสุด
-   ปัญหาที่ถูกรายงานบ่อยที่สุด
-   ความต้องการพัฒนาที่ถูกเลือกมากที่สุด

### 7.3 วิเคราะห์แยกกลุ่ม

-   เปรียบเทียบคะแนนตามบทบาท
-   เปรียบเทียบคะแนนตามหน่วยงาน
-   เปรียบเทียบคะแนนตามความถี่การใช้งาน
-   เปรียบเทียบผู้เคยใช้ระบบเดิมกับผู้ไม่เคยใช้ระบบเดิม
-   เปรียบเทียบผลตามช่วงเวลา/รอบการประเมิน

### 7.4 ข้อเสนอเพื่อการตัดสินใจ

ระบบอาจสร้างข้อความสรุปเชิงข้อมูล เช่น: - จุดแข็งที่ควรรักษา - จุดที่ควรตรวจสอบเพิ่มเติม -
ประเด็นที่ควรปรับปรุงเป็นลำดับแรก - ข้อมูลที่ยังไม่เพียงพอต่อการสรุป

**ห้ามให้ระบบสรุปว่าควรปรับปรุงหรือไม่จากคะแนนเฉลี่ยเพียงค่าเดียว**
ควรพิจารณาคะแนนรายหมวด จำนวนผู้ตอบ ปัญหาที่พบ และข้อมูลการทำงานจริงประกอบกัน

## 8. ข้อมูลสถิติจากระบบจริง (System Performance Data)

หากระบบต้นทางสามารถเชื่อมต่อ API หรือฐานข้อมูลได้
ควรนำข้อมูลจริงมาวิเคราะห์ร่วมกับแบบสอบถาม โดยแยกจากคะแนนความคิดเห็นของผู้ใช้

ตัวอย่างตัวชี้วัดสำหรับระบบแจ้งซ่อม: - จำนวนคำขอทั้งหมด - จำนวนงานเสร็จสิ้น -
จำนวนงานค้าง - จำนวนงานยกเลิก - อัตราการดำเนินงานจนเสร็จสิ้น -
ระยะเวลาเฉลี่ยตั้งแต่แจ้งจนมอบหมาย - ระยะเวลาเฉลี่ยตั้งแต่แจ้งจนเสร็จ -
จำนวนงานที่เกินระยะเวลาที่กำหนด - จำนวนครั้งที่เกิดข้อผิดพลาดของระบบ

ข้อกำหนด: - ห้ามสร้างข้อมูลสถิติจำลองแล้วแสดงเสมือนเป็นข้อมูลจริง -
หากยังไม่มีการเชื่อมต่อข้อมูล ให้แสดงสถานะว่า "ยังไม่มีข้อมูลจากระบบต้นทาง" -
ระบุแหล่งที่มาและช่วงเวลาของข้อมูล - แยกข้อมูลจากแบบสอบถาม (Perception)
กับข้อมูลจากระบบจริง (Operational Data) ให้ชัดเจน

## 9. แนวทางคำนวณและแปลผล

### 9.1 ค่าเฉลี่ยรายคำถามและรายหมวด

คำนวณจากคำตอบ Rating ที่มีคะแนน 1--5 เท่านั้น โดยไม่นำ N/A
หรือคำตอบที่ไม่เกี่ยวข้องมาคำนวณ

ค่าเฉลี่ยรายคำถาม:

`ค่าเฉลี่ย = ผลรวมคะแนนของผู้ตอบ / จำนวนคำตอบที่มีคะแนน`

ค่าเฉลี่ยรายหมวด:

`ค่าเฉลี่ยหมวด = ผลรวมคะแนนทุกคำตอบในหมวด / จำนวนคำตอบที่มีคะแนนในหมวด`

ควรแสดงจำนวนผู้ตอบ (n) กำกับค่าเฉลี่ยเสมอ เพื่อให้ผู้บริหารเห็นฐานข้อมูลที่ใช้คำนวณ

### 9.2 เกณฑ์แปลผลเบื้องต้น

  ค่าเฉลี่ย       ระดับ
  ------------ ---------
  4.51--5.00   มากที่สุด
  3.51--4.50   มาก
  2.51--3.50   ปานกลาง
  1.51--2.50   น้อย
  1.00--1.50   น้อยที่สุด

เกณฑ์นี้เป็นค่าเริ่มต้นที่ผู้ดูแลควรกำหนดหรือปรับได้ตามระเบียบ/กรอบการวิจัยของหน่วยงาน

### 9.3 หลักการแสดงผล

-   แสดงค่าเฉลี่ย จำนวนคำตอบ และจำนวน N/A
-   ไม่ตีความคำตอบปลายเปิดเป็นคะแนนโดยอัตโนมัติ
-   ไม่รวมคำถามคนละลักษณะเข้าเป็นคะแนนเดียวโดยไม่มีเหตุผล
-   ควรแสดงคะแนนรายหมวดมากกว่าพึ่งคะแนนรวมเพียงอย่างเดียว
-   หากจำนวนผู้ตอบน้อย ให้แจ้งเตือนว่าฐานข้อมูลยังจำกัด
-   การกำหนดเกณฑ์ "ผ่าน/ไม่ผ่าน" ต้องให้ผู้ดูแลกำหนดตามวัตถุประสงค์
    ไม่ควรตั้งเกณฑ์ตัดสินโดยไม่มีหลักเกณฑ์รองรับ

## 10. แนวทาง UX/UI

แนวทางหน้าจอ: 1. หน้าเลือก/เข้าสู่แบบประเมิน 2. หน้าแนะนำวัตถุประสงค์และคำชี้แจง 3.
แบบประเมินแบบ Stepper แบ่งเป็นขั้นตอน 4. แสดง Progress ว่าตอบไปแล้วกี่เปอร์เซ็นต์ 5.
ซ่อน/แสดงคำถามตามเงื่อนไขโดยไม่ทำให้ผู้ใช้สับสน 6. มีปุ่มย้อนกลับและไปต่อ 7.
ตรวจสอบคำถามบังคับก่อนส่ง 8. แสดงหน้าทบทวนคำตอบก่อนส่ง 9.
แสดงข้อความยืนยันเมื่อส่งสำเร็จ 10. รองรับ Desktop, Tablet และ Mobile

หลักการออกแบบ: - อ่านง่าย ไม่อัดคำถามจำนวนมากในหน้าเดียว - ใช้ภาษาที่ผู้ใช้ทั่วไปเข้าใจ
ไม่ใช้ศัพท์วิชาการเกินจำเป็น - คำถามหนึ่งข้อควรวัดประเด็นเดียว - ไม่ชี้นำคำตอบ - มีตัวเลือก
"ไม่เกี่ยวข้อง/ไม่สามารถประเมินได้" ในคำถามที่เหมาะสม -
ไม่บังคับเก็บชื่อหรือข้อมูลระบุตัวบุคคล หากไม่จำเป็น -
แจ้งผู้ตอบให้ทราบว่าข้อมูลจะถูกนำไปใช้เพื่ออะไร

## 11. ข้อกำหนดด้านความถูกต้องและความน่าเชื่อถือ

1.  แบบประเมินต้องแยก "ประสิทธิภาพ", "ประสิทธิผล", "ความพึงพอใจ" และ
    "ข้อมูลเชิงข้อเท็จจริง" ไม่ใช้แทนกัน
2.  คำถามที่ผู้ตอบไม่มีประสบการณ์ตรงต้องมีตัวเลือก N/A หรือไม่แสดงคำถามนั้น
3.  ต้องมีเงื่อนไขป้องกันคำตอบขัดแย้งกัน เช่น เลือก "ไม่พบปัญหา"
    แล้วไม่ควรเลือกปัญหาอื่นพร้อมกัน
4.  คำถามเปรียบเทียบระบบเดิมควรแสดงเฉพาะผู้ที่เคยใช้ระบบเดิม
5.  คำถามเฉพาะบทบาทต้องแสดงตามบทบาทที่เลือก
6.  คำตอบทุกชุดต้องอ้างอิงแบบประเมินและเวอร์ชันที่ตอบ
7.  ต้องมีการตรวจสอบข้อมูลซ้ำและการส่งคำตอบซ้ำตามนโยบายที่กำหนด
8.  ควรมีการทดสอบความเข้าใจของคำถาม (Pilot Test) ก่อนนำไปใช้งานจริง
9.  หากใช้เพื่อการวิจัยหรือเผยแพร่ทางวิชาการ
    ต้องตรวจสอบความตรงของเนื้อหาและความเชื่อมั่นของเครื่องมือเพิ่มเติมตามวิธีวิจัยที่เลือก
10. ต้องคำนึงถึงสิทธิ์เข้าถึงข้อมูลและความเป็นส่วนตัวของผู้ตอบ

## 13. ตัวอย่าง Specific Indicators: ระบบแจ้งซ่อมและบำรุงรักษา

ใช้เป็นชุดตัวอย่างสำหรับระบบแรก ไม่ใช่ข้อกำหนดตายตัวของทุกระบบ

### บริบทของระบบ

-   ผู้ใช้งาน 5 กลุ่ม: ผู้แจ้งซ่อม, หัวหน้าสำนักงานเลขานุการ, เจ้าหน้าที่ซ่อม, เจ้าหน้าที่พัสดุ,
    ผู้บริหาร
-   Workflow 8 สถานะ:
    1.  แจ้งซ่อม
    2.  มอบหมายงาน
    3.  อยู่ระหว่างดำเนินการ
    4.  จัดซื้อวัสดุ/อะไหล่
    5.  ประสานงานบริษัทภายนอก
    6.  อนุมัติ/รอวัสดุหรืออยู่ระหว่างซ่อม
    7.  เสร็จสิ้น
    8.  ยกเลิก
-   เส้นทางงาน 3 รูปแบบ:
    -   Path A: ซ่อมเอง --- แจ้งซ่อม → มอบหมายงาน → ดำเนินการ → เสร็จสิ้น
    -   Path B: จัดซื้อวัสดุ --- แจ้งซ่อม → มอบหมายงาน → ดำเนินการ → จัดซื้อวัสดุ →
        รอ/อนุมัติและซ่อม → เสร็จสิ้น
    -   Path C: ประสานบริษัท --- แจ้งซ่อม → มอบหมายงาน → ดำเนินการ →
        ประสานบริษัท → เสร็จสิ้น

### Specific Questions ที่ควรเพิ่ม

-   ระบบรองรับเส้นทางการซ่อมที่แตกต่างกันได้เหมาะสมหรือไม่
-   การเปลี่ยนสถานะงานสอดคล้องกับขั้นตอนการปฏิบัติงานจริงหรือไม่
-   สามารถตรวจสอบผู้รับผิดชอบในแต่ละช่วงได้หรือไม่
-   การจัดซื้อวัสดุ/อะไหล่มีข้อมูลครบถ้วนและตรวจสอบได้หรือไม่
-   การประสานบริษัทภายนอกสามารถบันทึกและติดตามความคืบหน้าได้หรือไม่
-   สามารถบันทึกผลการซ่อมและภาพหลังซ่อมได้ครบถ้วนหรือไม่
-   ผู้บริหารสามารถดูจำนวนงานค้าง งานเสร็จ และงานยกเลิกได้หรือไม่
